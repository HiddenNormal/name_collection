# 从人名数据集得到 IPA 发音：方法说明

> 数据集：`external/name_dataset.zip` — 105 个国家、491,655,925 条记录、未压缩约 10 GB
> 目标用途：**TTS 朗读人名**（所以除了 IPA，还关心重音、音节、以及能不能直接喂给语音合成器）

---

## 0. 一句话结论

**不要给 4.9 亿条记录逐条算发音。** 实测：491,655,925 条记录去重后只有 **67,736,023 个唯一 token**
（1 : 7.3 的压缩），按国家展开也只有约 **1.03 亿个**「token × 国家」发音单元。
espeak-ng 单核能跑 2.6–6 万 token/秒，**全量生成 IPA 只要约 1 小时**。
所以真正的问题不是算力，而是「语言判定 + 高频名字的准确性」。

落地的技术路线：

```
原始 CSV ──①规范化+过滤──▶ 唯一 token 清单 ──②文字系统检测──▶ ──③语言判定──▶
        ──④IPA 解析级联（词典优先 → G2P 兜底 → 标记未解决）──▶ name→IPA 词典
        ──⑤回填──▶ 带 IPA 的原数据集
```

核心引擎选型：**espeak-ng**（已在 Windows 上验证可用，137 种语言 / 222 个声音，直接输出带重音的 IPA，
并且是开源 TTS 生态 Piper / Coqui 的标准 phonemizer——天然衔接你的 TTS 目标）。

## 1. 先看清数据（这决定了方法长什么样）

### 1.1 基本结构

| 项 | 值 |
|---|---|
| 记录数 | 491,655,925（原始文件描述；本仓库另有精确统计） |
| 国家文件数 | 105 个 CSV（`data/<ISO2>.csv`） |
| 行格式 | `first_name,last_name,gender,country_code`，**无表头** |
| gender | `M` / `F` / 空 |
| 重复 | 未去重（同一行可大量重复） |
| 字符集 | UTF-8，字段内可能有多词（`Anne Marie`）和引号内逗号 |

### 1.2 一个反直觉但很关键的事实：数据绝大多数是拉丁字母

数据集的「国家」是人的国籍/所在地，**不是文字的书写系统**。实测（对 105 个文件做随机偏移采样）：

| IN | 98.1% | 天城文 1.4% |
| HK | 97.5% | 汉字 2.5% |
| CN | 95.7% | 汉字 3.6% |
| JP | 94.4% | 汉字 3.8% + 假名 1.5% |
| TW | 89.0% | 汉字 **10.9%** |
| BD | 89.7% | 孟加拉文 10.2% |
| GE | 85.7% | 格鲁吉亚文 9.8% + 西里尔 4.4% |
| GR | 80.5% | 希腊文 17.7% |
| KH | 67.6% | 高棉文 **31.3%** |
| IL | 61.4% | 希伯来文 22.2% + 阿拉伯文 14.0% |
| AF | 60.7% | 阿拉伯文 39.3% |
| SA | 68.4% | 阿拉伯文 30.6% |
| JO | 50.0% | 阿拉伯文 49.8% |
| EG | 50.5% | 阿拉伯文 49.5% |
| KR | 49.1% | 谚文 **50.8%** |
| KZ | 26.3% | 西里尔 **73.7%** |

**按「出现次数」加权**（把国家规模算进去，全数据集约 9.83 亿个名字出现次数）：

| 文字 | 占全部名字出现次数 |
|---|---|
| 拉丁 Latn | **82.9%** |
| 阿拉伯 Arab | **14.4%** |
| 西里尔 Cyrl | 2.1% |
| 希伯来 Hebr | 0.26% |
| 孟加拉 Beng | 0.15% |
| 汉字 Hani | 0.05% |
| 其余（天城/希腊/谚文/埃塞/高棉…） | < 0.1% |

**非拉丁文字合计约占 17.1%**（若按「整词主导文字」统计则略高，约 17–22%）。
贡献最大的是 EG（占全部非拉丁出现次数的 26.6%）、IQ（15.2%）、SA（10.8%）、RU（8.9%）、SD（8.8%）。

**结论：主要难点不是「多文字转写」，而是「拉丁字母名字要按哪个语言的规则读」。**
只有约 25 个国家含显著非拉丁文字量；其余 80 个国家几乎全是拉丁字母——但同一个拉丁拼写在不同语言里
发音完全不同（这才是真正的难点）。同时要注意：**阿拉伯文字按记录量算占 14%（不是可以忽略的边角）**，
且它恰恰是最难做对的部分（见 §4）。

### 1.3 ⚠️ 采样陷阱（做统计时必读）

各国家 CSV **沿文件长度是非同质的**，表头采样会得出完全错误的结论：

| 文件 | 前 20,000 行 | 全文件随机偏移采样 |
|---|---|---|
| `EG.csv` | 99.9% 拉丁 | **50.5% 拉丁 / 49.5% 阿拉伯** |
| `SA.csv` | 100% 拉丁 | **68.4% 拉丁 / 30.6% 阿拉伯** |
| `JO.csv` | 59% 拉丁 | **50% 拉丁 / 50% 阿拉伯** |

→ 任何抽样都必须用**随机字节偏移**或**全量扫描**，不能只读文件开头。

### 1.4 数据质量问题（TTS 场景下尤其要紧）

观察到的脏数据形态：

| 类型 | 实例 |
|---|---|
| 空字段 | `,,M,EG` |
| 装饰字符（阿拉伯文的拉伸符 U+0640 与音符） | `تہٰٰہٰٰہٰٰہٰٰامر٭ﹾﹾ٭` |
| 前缀下划线 / 框线符号 | `_Aya`、`╚► Rasha` |
| 多词名 | `Anne Marie`、`Abd Elkarim`、`Abu Reem` |
| 非本国语言名 | `JP.csv` 里的 `Mohammad,Riaz Rahat`；`CN.csv` 里的 `Ann,Liao` |

→ 必须先过滤/规范化，否则会把算力浪费在合成垃圾上。**规范化规则由 `profile/normalize.py` 给出**。

### 1.5 去重的规模（这是本方法成立的基础）

精确统计（duckdb 全量扫描 105 个文件，186.5 秒）：

| 指标 | 数值 |
|---|---|
| 记录总数 | **491,655,925**（与 `description.txt` 完全一致） |
| 全局唯一 first name | **30,894,739** |
| 全局唯一 last name | **36,841,284** |
| **全局唯一 token 合计（原始）** | **67,736,023** |
| **全局唯一 token（规范化后，精确）** | **59,791,550** ← 规范化又去掉 11.7% 的工作量 |
| 按「token × 国家」计的发音单元 | 45,905,862（first）+ 56,958,836（last）= **102,864,698** |
| 规范化后按国家去重 | 101,592,045（折叠系数 1.0125×） |
| 空 first / 空 last | 977,877 / 2,024,552 |
| 空 gender | 92,722,868（占 18.86%） |
| gender 非法值 | 0 |

**压缩比：491.6M 条记录 → 67.7M 唯一 token（1 : 7.3）→ 规范化后 59.8M。**
这一步把问题从「不可行」变成「可行」。

> 注：规范化对不同文字的收益不同——拉丁/西里尔几乎只是大小写折叠（1.000–1.005×），
> 而阿拉伯文字有 1.018–1.072×（装饰符变体被合并，如 EG 5,591,135 → 5,294,113）。

### 1.6 覆盖度曲线——决定「该把精力花在哪里」

按全局频次排序后，前 N 个 token 覆盖了多少条记录：

| 前 N 个 token | first name 覆盖率 | last name 覆盖率 |
|---|---|---|
| 1,000 | 36.7% | 21.5% |
| 10,000 | **65.6%** | 42.6% |
| 100,000 | 82.5% | 65.5% |
| 1,000,000 | **90.6%** | 83.7% |
| 10,000,000 | 95.7% | 94.2% |

这张表是整个方案的策略依据：
- **前 1 万个 first name 就覆盖 65.6% 的记录** → 这一档值得用最高质量手段（词典 + 人工校核）。
- 前 100 万 token 覆盖 90.6% → 这一档用 espeak 自动生成足够。
- 剩下 6000 多万 token 只贡献 9.4% 的记录 → 自动生成 + 标记低置信度即可，不必追求准确。

**分档处理是控制成本和质量的关键，而不是一视同仁。**

## 2. 方法：五级流水线

### ① 规范化 + 过滤（`profile/normalize.py`）

保留「原始写法」和「规范化键」两列：

- Unicode **NFC** 归一化
- 去除首尾空白、合并连续空白
- 去除装饰字符：阿拉伯文 tatweel `U+0640`、阿拉伯文附加音符（U+064B–U+065F、U+0670）、
  零宽字符（U+200B–U+200F、U+FEFF）、框线/箭头符号（`_`、`╚`、`►` 等）
- 剔除明显非人名：纯数字、纯标点、单字符、超长（>60）
- **不**做大小写折叠（保留原样展示），但用小写形式做词典键
- 多词名保留内部空格（G2P 时逐词处理）

### ② 文字系统检测（每个 token）

按 Unicode 区段判定：Latn / Cyrl / Arab / Hebr / Grek / Geor / Khmr / Hang / Hani / Kana /
Ethi / Thaa / Beng / Deva / Taml / Telu / Knda / Mlym / Gujr / Guru / Mymr。
这是**最强的语言先验信号**：Cyrillic token 几乎不可能是法语名。

### ③ 语言判定（国家 × 文字）

`docs/country_languages.csv`（105 行，已校验每个 voice 都真实存在于 espeak）给出：

```
country, primary_voice, primary_language, secondary_voices, scripts, notes
```

判定规则：

```
lang(token) = f(script, country)
  ├─ 若 script ≠ Latn：用 country 的 non-Latin 对应 voice（如 RU→ru, EG→ar, KR→ko）
  ├─ 若 script = Latn：用 country 的 primary_voice（如 FR→fr-fr, US→en-us, BR→pt-br）
  │   └─ 特例：CN/TW 的拉丁 token 多为拼音 → 优先 cmn-latn-pinyin
  └─ 兜底：country 的 secondary_voices，再兜底 en-us
```

**必须处理同形异读（homograph）**：键是 `(normalized_token, lang)`，不是 token。
同一个 `Jean` 在 FR 和 US 是两条不同的记录：

| token | lang | IPA |
|---|---|---|
| Jean | fr-fr | `ʒˈɑ̃` |
| Jean | en-us | `dʒˈiːn` |
| Laure | fr-fr | `lˈɔʁ` |
| Laure | en-us | `lˈɔːɹə` |

（以上为 espeak-ng 1.52 实测输出。）

### ④ IPA 解析级联（每个 (token, lang)）

按质量从高到低：

1. **词典查表** — WikiPron（OpenSLR 94，约 260 万条、200+ 语言的 IPA，来自 Wiktionary）/
   CMUdict（英语）/ 自建高频名表。查到即用，质量最高、重音最准。
2. **主 G2P** — espeak-ng 用该语言的 voice 生成 IPA。
3. **兜底 G2P** — 该国的 secondary voice，再不行用 `en-us`。
4. **未解决** — 记录原因（空 token / 不支持的文字如高棉、迪维希 / 引擎报错）。

每条结果都写入 **溯源字段**，这是整个方案可维护的关键：

```
source     ∈ { lexicon:wikipron, lexicon:cmudict, g2p:espeak, g2p:charsiu, unresolved }
confidence ∈ { high, medium, low }
reason     （未解决时的人类可读原因）
```

### ⑤ 回填 + 交付

- `output/name_ipa_lexicon.parquet` — 可复用的 `(token, lang) → IPA` 词典 + 频次 + 溯源
- `output/dataset_with_ipa/<CC>.parquet` — 按国家分片的原数据 + `first_ipa` / `last_ipa` / `lang_*` / `source_*`

### 3.0 实测基准（`g2p_eval/EVAL_REPORT.md`，27 种语言、每语言 400–4,000 条 gold）

评测口径说明很重要：WikiPron 的 gold 是**没有重音标记**的、且采用 Wiktinary 的转写习惯，
而 espeak 用自己的 IPA 习惯（`ɭ` vs `lʲ`、`ɜ` vs `ɐ`）。所以直接比字符串会测出「转写习惯差异」
而不是发音质量（俄语字符串 PER 高达 0.45，但发音其实是好的）。因此主指标用
**panphon 特征加权的 PER（`PER_feat`）**——`ɪ→i`、`l→ɭ` 几乎不罚分，真错误才罚分。

| 语言 | espeak `PER_feat` | 最佳引擎 | 说明 |
|---|---|---|---|
| ell 希腊 | **0.024** | espeak | 优秀 |
| ind 印尼 | **0.026** | espeak | 优秀 |
| fra 法语 | **0.028** | espeak | 优秀（exact 0.686） |
| ces 捷克 | **0.041** | espeak | 优秀 |
| ita 意大利 | 0.054 | espeak | 很好 |
| spa 西班牙 | 0.060 | epitran 0.017 | epitran 略优但**无重音** |
| nld 荷兰 | 0.093 | espeak | 好 |
| eng 英语 | **0.111**（CMUdict gold） | espeak | 重音准确率 **0.79**（15,941 个真实名字） |
| swe 瑞典 | 0.114 | espeak | 好 |
| eng_cmu_names | 0.123 | espeak | 真实名字子集 |
| hin 印地 | 0.129 | espeak | 良 |
| ara 阿拉伯 | 0.174 | espeak | 中等 |
| deu 德语 | 0.185 | espeak | 中等 |
| rus 俄语 | 0.146 | epitran 0.146 | 相当 |
| jpn 日语 | 0.127 | **espeak-plus**（pykakasi 汉字→假名） | 必须先做汉字→假名 |
| kor 韩语 | 0.290 | epitran 0.131 | epitran 略优但**无重音** |
| heb 希伯来 | **0.466** | espeak | 差（无元音标记） |
| dan 丹麦 | 0.397 | espeak | 差（丹麦语拼写-发音极不规则） |
| cmn 中文 | 0.659 | epitran 0.532 | 都差；**espeak 声调准确率 0.0** |

**关键结论：几乎所有语言都是 espeak 最好或并列最好；而 Epitran / WikiPron 词典虽然少数语言分段
PER 更低，但完全不输出重音——这对 TTS 是致命缺陷。** 所以路由表很简单：**espeak 做主干**。

### 3.0.1 词典层（WikiPron）到底值不值得加

WikiPron 只有 **约 260 万条**，覆盖真实名字的能力随频率急剧下降：

| 语言 | top-100 名字覆盖 | top-1000 | top-5000 |
|---|---|---|---|
| fin / pol | 1.00 | 0.53–0.67 | 0.25–0.29 |
| eng | 0.96 | 0.70 | 0.37 |
| ces / ita / fra | 0.91–0.96 | 0.49–0.53 | 0.24 |
| spa / hun / por | 0.72–0.88 | 0.38–0.49 | 0.18–0.26 |
| rus / tur / nld / deu | 0.43–0.78 | 0.23–0.31 | 0.10–0.15 |
| ara / kor / ind | 0.11–0.30 | 0.15–0.22 | 0.11–0.14 |
| cmn / hin / jpn | **0.00** | 0.00–0.01 | 0.01–0.02 |

**结论：词典只能当「高频名字的质量加成」，不能当主路径。** 而且 WikiPron **完全没有重音标记**
（CMUdict 有 99.9%），所以即使查到了词典，对 TTS 来说也缺重音——除非该语言本来就不标重音。

### 3.1 ⚠️ 最重要的一个实测发现：native voice 会把拉丁字母读成英语

这是本项目最容易踩的坑，实测确认：

| voice | `Laure` | `Smith` | 说明 |
|---|---|---|---|
| `en-us` | `lˈɔːɹə` | `smˈɪθ` | 基准 |
| `ru` | `lˈɔːɹə` | `smˈɪθ` | **与 en-us 完全相同** |
| `ar` / `el` / `ko` / `ka` / `he` / `kk` / `bg` / `cmn-latn-pinyin` | `lˈɔːɹə` | `smˈɪθ` | **全部与 en-us 相同** |
| `ja` | `ˈɛl ˈeɪ jˈuː ˈɑː ˈiː` | — | **逐字母拼读**（更糟） |
| `fr-fr` | `lˈɔʁ` | `smˈɪθ` | 真的在做法语 LTS |
| `de` / `tr` / `pl` / `sr` / `az` / `tk` / `vi` | 各自不同 | — | 真的在做本国 LTS |

**结论**：当某个 voice 的语言本身不用拉丁字母书写时，espeak 对拉丁输入会**静默回退到英语 LTS**。
所以「用俄语 voice 读俄国的拉丁字母名字」并不会得到俄语发音，而是英语发音——而且你不会收到任何警告。

**这直接决定 voice 选择策略**：

```
if token 是拉丁字母:
    if 国家主语言本身用拉丁字母（法/德/西/葡/荷/北欧/波/捷/匈/罗/土/阿塞/土库曼/塞尔维亚拉丁/越/马来/印尼…）
        → 用该语言 voice（真 LTS）
    elif 国家是 CN / TW:
        → 用 cmn-latn-pinyin（合法的拼音会正确处理，非拼音自动回退英语）
    elif 国家是 HK / MO:
        → 用 yue-latn-jyutping
    else:                       # RU/BG/KZ/EG/SA/GR/IL/GE/KR/JP/KH… 的拉丁名字
        → 显式用 en-us（既然结果必然是英语，就不要假装是本地发音）
else:                            # 非拉丁文字
    → 用该国对应文字的 voice（KZ→kk, RU→ru, EG→ar, IR→fa, GR→el, IL→he, GE→ka,
                              KR→ko, CN/TW→cmn, HK/MO→yue, JP→ja, BD→bn, IN→hi …）
```

含义：**对这个数据集来说，约 20% 的高频 token 实际拿到的是「英语发音」**——
因为它们是非拉丁文字国家里的拉丁字母写法（转写形态）。这不是 bug，而是需要**显式记录**的设计决策：
在输出里用 `lang_reason = english-fallback` 标出来，下游就知道这一条不是本地语发音。

如果这一档需要更准，可选增强：先做**拉丁 → 原文字的回写转写**（如 `Natalia`→`Наталья`）再走本地 voice。
这是一条明确、可量化的改进路径。

### 3.2 其它关键工程坑（已验证）

1. **Windows 控制台会破坏非 ASCII 参数**：PowerShell 里 `espeak-ng ... "Наталья"` 会变成乱码。
   解法：把文本写进 UTF-8 文件用 `-f` 传入，或（更好）用 `ctypes` 调 `libespeak-ng.dll`。
   这不是 espeak 的 bug。
2. 输出里可能夹带**语言切换标记** `(en)` `(cmn)` `(ja)`，需后处理剥掉。
3. **声调数字**会保留（`wˈa5ŋɡ`、泰语 `sa2mˈa2cha2sj`）。建议原样保留并文档化。
4. `-v ja "田中"` 在 espeak 1.52 上是**坏的**（输出 `(en)tʃˈaɪniːz(ja)lˈe̞tə`）——
   日语汉字 token 必须标 `confidence=low`。
5. 英语 voice 读外来名会「英国化」：`en-us "Xiong"` → `kʃˈəŋ`（应为 `ʃjʊŋ`），
   `en-us "Nguyen"` → `nˈuːjɛn`。**这是设计意图而非 bug**——但意味着 US 数据里的大量
   族裔名会有明显误差，需要靠词典或语言检测修正。

## 4. 质量天花板（诚实评估）

这些是方案的结构性限制，不是实现问题：

| 限制 | 影响范围 | 说明 |
|---|---|---|
| **阿拉伯文/希伯来文省略短元音** | EG/SA/IQ/SD/YE/JO/LY/SY/PS/IL 等 | 文字本身不写短元音，元音只能猜；这是最大误差源 |
| **日语汉字读音** | JP 3.8% 汉字 | 需要读音词典，espeak 失败；须降级或人工 |
| 无 voice 的语言 | KH（高棉 31%）、MV（迪维希）、PH（他加禄）、BI（基隆迪）、NG（约鲁巴/伊博/豪萨） | 只能兜底到英语，质量差 |
| espeak 用 MSA 近似地方阿拉伯语 | EG/MA/DZ/TN | 埃及/摩洛哥口语与 MSA 有差异 |
| 英语语境下外来名 | US/CA/GB/AU | `Xiong`、`Nguyen` 类会被英语化 |
| 低频/异常拼写名 | 全局长尾 | G2P 必然出错，占记录数比例低但占 token 数比例高 |
| 同形异读无法完全消歧 | 全局 | 只能靠国家先验，无法 100% 正确 |

**结论**：高频名字（覆盖大部分记录）质量可用；长尾必然有错。
如果这个数据要进生产，正确做法是：**高频 top-N 人工校核 + 长尾自动生成并标记置信度**，
而不是假装全都对。

## 5. 给 TTS 的落地建议

1. **IPA 只是中间产物**，TTS 真正需要的是「音素 + 重音 + 音节」。espeak 同时给 IPA 和
   它自己的 phoneme 串，二者一致，取 phoneme 串直接进 Piper 之类的音素级 TTS。
2. **重音符号必须保留**（`ˈ` 主重音、`ˌ` 次重音）。丢掉重音会让英语/荷兰语/德语/俄语名字
   听感明显变差。
3. **语言选择比引擎选择更重要**：同一个名字用错语言的 voice，比用次一点的引擎错得更离谱。
4. **多词名**逐词 G2P 后拼接；注意 `van`/`von`/`de`/`bin` 之类的前缀在部分语言中要轻读/连读。
5. **跨语言场景**：如果 TTS 是英语音色要读法语名，有两种策略——
   (a) 用原语言 IPA（「正确」但夹在英语句中会突兀）；
   (b) 先取原语言 IPA，再映射到目标语言音素表（更自然）。
   本方案默认给 (a)，(b) 作为后续可选层。

## 6. 规模与成本（实测数据）

### 6.1 计算量

| 项 | 数值 |
|---|---|
| 需要发音的单元 | 102,864,698 个 `(token, 国家)` |
| espeak-ng 吞吐（ctypes，单核） | **26,000 – 60,000 token/秒**（视语言而定） |
| 全量 G2P 预计耗时 | **约 30 – 70 分钟（单核）** |
| 数据扫描（duckdb，8 线程） | 10 GB / 491M 行，**186 秒** |

**结论：发音生成本身不是瓶颈，甚至算不上成本项。** 真正的工程成本在：
1. 语言判定正确率（决定质量上限）
2. IO 与 join（10 GB 输入 → 约 15–25 GB parquet 输出）
3. 高频名字的**人工校核**

这意味着一件很重要的事：**你完全可以把「前 100 万 token」这一档做得很扎实**（覆盖 90.6% 的记录），
而不是被迫只能抽样。

### 6.2 存储预估

| 产物 | 规模 |
|---|---|
| `name_ipa_lexicon.parquet`（67.7M token × ~10 列，zstd） | 约 3–6 GB |
| `dataset_with_ipa/`（491M 行 × 10 列，zstd，按国家分片） | 约 15–25 GB |
| demo 音频（500 条 WAV，22050 Hz） | 约 15 MB |

### 6.3 建议的执行顺序（按性价比）

1. **第 1 天**：跑通全量 token 去重 → 语言判定 → espeak 生成（约 1 小时）→ 得到 67.7M 词的词典。
2. **第 2 天**：对 **top 1 万 first name + top 1 万 last name** 做人工/词典校核
   （覆盖 65.6% / 42.6% 的记录，人工量约 2 万个 token，完全可做）。
3. **第 3 天**：把校核结果合并回词典，生成最终 `dataset_with_ipa`。
4. **持续**：长尾错误靠用户反馈/抽样发现，逐步补词典——因为词典是「一次投入、永久复用」的资产，
   而原数据集里每个名字平均重复 7 次，所以**修正一个 token 等于修正 7 条记录**。

## 7. 端到端实测验证（Lead 独立跑通）

为了证明这套方法真的能跑，我在全 105 个国家上各取「频率最高的 120 个 first name + 120 个 last name」
（经 `normalize.py` 过滤后共 25,200 个 token），完整走了一遍「规范化 → 文字检测 → 语言判定 → espeak 生成」：

| 指标 | 结果 |
|---|---|
| 抽样 token 数 | 25,200（105 国 × 2 字段 × ≤120） |
| **成功产出 IPA** | **25,148（99.79%）** |
| 未解决 | 52（全部是 **高棉文**——espeak 无 km voice） |
| G2P 吞吐 | **16,268 token/秒**（25,200 个只用 1.5 秒） |
| 最差国家 | KH 79.2%（高棉文）；其次 CZ / LT 99.6% |

语言判定分布（这个数字很说明问题）：

| `lang_reason` | token 数 | 占比 | 含义 |
|---|---|---|---|
| `country-latin-lts` | 16,377 | 65.0% | 本国语言用拉丁字母 → 真本地发音 |
| `english-fallback` | 5,187 | **20.6%** | 非拉丁文字国家的拉丁写名 → **英语发音**（见 §3.1） |
| `script:default` | 1,880 | 7.5% | 非拉丁文字 → 该文字默认 voice |
| `pinyin-latn` | 960 | 3.8% | CN/TW 拼音名 → 拼音 voice |
| `script:country` | 744 | 3.0% | 非拉丁文字 → 该国专属 voice（kk/bg/tk/sr/fa…） |
| `unsupported-script` | 52 | 0.2% | 高棉文/塔纳文 → 无 voice |

**这张表本身就是结论**：65% 的发音是「拉丁语言的真 LTS」，20.6% 是「英语回退」，
只有约 14.5% 走非拉丁文字路径（这是**按 token 个数**加权；若**按名字出现次数**加权，
非拉丁文字约占 17.1%，见 §1.2）。也就是说——**做这个项目的核心工作量在拉丁字母名字的语言判定上，
而高价值的非拉丁部分集中在阿拉伯文/西里尔文**（后者按记录量占 14.4% / 2.1%，且阿拉伯文是最难做对的）。

产物：`work/lead_scan/verify_tokens.parquet`（25,200 行，含 raw/norm/script/lang/lang_reason/ipa/source）
与 `work/lead_scan/verify_summary.json`。
